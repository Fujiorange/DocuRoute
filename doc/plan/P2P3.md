# P2P3: Project Templates - Implementation Prompt

## Context

You are implementing **Phase 2, Prompt 3 (P2P3)** for **DocuRoute**, an ISO 9001 compliant document management system for shipbuilding, offshore platforms, and heavy industrial projects. DocuRoute is a pnpm monorepo with:
- **apps/web**: Next.js 14 app with NextAuth v4.24.13, TypeScript, Tailwind CSS
- **apps/worker**: Node.js BullMQ worker for background jobs
- **packages/db**: Prisma ORM with PostgreSQL (Supabase)
- **packages/core**: Shared business logic (no React/Next.js imports)
- **packages/types**: Shared TypeScript types
- **packages/emails**: React Email templates

**Phase 1 Status**: User authentication, PBAC authorization, document management, project management, custom roles, invitations, search, and notifications are fully implemented.

**Phase 2 Progress**: P2P1 (Equipment Hierarchy Management) is complete.

**Your Mission**: Implement Project Templates to allow organizations to clone folder structures, equipment lists, workflow sequences, and document checklists across similar projects (e.g., 4 identical vessels, 10 offshore modules) without manual recreation.

---

## Requirements

### Business Context

Organizations repeat similar project structures across multiple builds. Templates enable:
1. **Cloning** folder hierarchies, equipment trees, workflows, and checklists
2. **Sandbox mode** for "what-if" testing before making changes to live projects
3. **Change proposals** for controlled updates to active projects
4. **Template marketplace** (optional) for industry-standard templates

**CRITICAL SAFETY RULE**: Template changes MUST NOT cascade to existing projects automatically. This prevents the "INSANELY DANGEROUS" scenario where a template modification affects all active projects.

```prisma
model ProjectTemplate {
  id                  String   @id @default(cuid())
  companyId           String
  name                String
  description         String?
  category            String   // "NEWBUILD_VESSEL" | "OFFSHORE_PLATFORM" | "REFINERY_MODULE" | "CUSTOM"
  isPublic            Boolean  @default(false)  // If true, available to all companies (requires PLATFORM_ADMIN approval)

  createdBy           String
  createdAt           DateTime @default(now())
  updatedAt           DateTime @updatedAt

  company             Company  @relation(fields: [companyId], references: [id])

  // Relational structure (v2.1 - CRITICAL FIX)
  equipmentItems      TemplateEquipment[]
  folders             TemplateFolder[]
  workflowStages      TemplateWorkflowStage[]
  checklistItems      TemplateChecklistItem[]
  projects            Project[]  // Projects created from this template

  @@index([companyId, category])
}

// v2.1: Relational equipment structure (replaces equipmentStructure Json)
model TemplateEquipment {
  id              String           @id @default(cuid())
  templateId      String
  tag             String           // "HVAC-FAN-001"
  name            String
  equipmentType   String
  parentTag       String?          // For hierarchy (references another TemplateEquipment.tag)
  level           Int              // Depth in hierarchy (1 = top-level)
  sortOrder       Int              @default(0)

  // Optional fields
  manufacturer    String?
  modelNumber     String?
  criticalityLevel String?

  template        ProjectTemplate  @relation(fields: [templateId], references: [id], onDelete: Cascade)

  @@unique([templateId, tag])
  @@index([templateId, parentTag])
  @@index([templateId, equipmentType])
}

// v2.1: Relational folder structure (replaces folderStructure Json)
model TemplateFolder {
  id              String           @id @default(cuid())
  templateId      String
  name            String
  parentId        String?          // Self-referential for hierarchy
  level           Int
  sortOrder       Int              @default(0)
  requiredPermissions String[]     // Permissions required to access folder

  template        ProjectTemplate  @relation(fields: [templateId], references: [id], onDelete: Cascade)
  parent          TemplateFolder?  @relation("FolderHierarchy", fields: [parentId], references: [id])
  children        TemplateFolder[] @relation("FolderHierarchy")

  @@index([templateId, parentId])
}

// v2.1: Relational workflow stages (replaces workflowSequence Json)
model TemplateWorkflowStage {
  id                      String           @id @default(cuid())
  templateId              String
  stageName               String           // "IFR", "IFA", "IFC", "AS_BUILT"
  stageOrder              Int              // 1, 2, 3, 4
  requiredPermissions     String[]
  autoTransitionCondition String?          // "ALL_DOCS_APPROVED" | "PM_APPROVAL" | null

  template                ProjectTemplate  @relation(fields: [templateId], references: [id], onDelete: Cascade)

  @@unique([templateId, stageOrder])
  @@index([templateId])
}

// v2.1: Relational checklist items (replaces checklistTemplate Json)
model TemplateChecklistItem {
  id              String           @id @default(cuid())
  templateId      String
  itemText        String
  category        String           // "PRE_SUBMISSION" | "REVIEW" | "APPROVAL" | "HANDOVER"
  sortOrder       Int              @default(0)
  isRequired      Boolean          @default(true)
  applicableDocTypes String[]      // ["DRAWING", "DATASHEET", "MANUAL"]

  template        ProjectTemplate  @relation(fields: [templateId], references: [id], onDelete: Cascade)

  @@index([templateId, category])
}

// Update existing Project model
```

### API Endpoints

Implement the following API routes in `apps/web/src/app/api/`:

1. **POST /api/project-templates** - Create template from existing project
   - Input: `{ projectId, name, description, category }`
   - Output: Template ID with all equipment, folders, workflows, checklists
   - Permission: `PROJECT_TEMPLATE_CREATE`

2. **GET /api/project-templates?category={cat}** - List available templates
   - Query params: `category`, `isPublic`, `search`
   - Returns: Templates with item counts (equipment, folders, stages, checklist items)
   - Permission: `PROJECT_VIEW`

3. **GET /api/project-templates/{id}** - Get template details
   - Returns: Full template with all nested structures
   - Permission: `PROJECT_VIEW`

4. **DELETE /api/project-templates/{id}** - Delete template
   - Validation: Cannot delete if projects are using it
   - Permission: `PROJECT_TEMPLATE_DELETE`

5. **POST /api/projects/{id}/apply-template** - Apply template to new project
   - Input: `{ templateId }`
   - Validation: Project must be empty (no equipment, no documents)
   - Creates: Equipment, folders, workflow stages, checklist items
   - Logs: AuditVaultEntry with full template snapshot
   - Permission: `PROJECT_TEMPLATE_APPLY`

6. **POST /api/projects/{id}/sandbox** - Create sandbox clone
   - Creates: Read-only copy of project with `isSandbox=true`
   - Returns: Sandbox project ID
   - Permission: `PROJECT_SANDBOX_CREATE`

7. **POST /api/projects/{id}/apply-sandbox-changes** - Promote sandbox to live
   - Input: `{ sandboxId, changeProposalText }`
   - Validation: Requires approval if user lacks `PROJECT_CHANGE_APPROVE`
   - Creates: Change proposal workflow
   - Logs: Full diff in audit vault
   - Permission: `PROJECT_SANDBOX_CREATE` (for proposal), `PROJECT_CHANGE_APPROVE` (for approval)

### Core Business Logic

Implement in `packages/core/src/templates.ts`:

#### Template Creation
```typescript
async function createTemplateFromProject(
  projectId: string,
  templateName: string,
  templateDescription: string,
  category: ProjectTemplateCategory,
  createdBy: string
): Promise<string> // Returns templateId
```

**Behavior**:
1. Fetch all equipment from project (with hierarchy)
2. Fetch all folders (with hierarchy)
3. Fetch workflow configuration
4. Create template with relational structures
5. Log template creation to audit trail

#### Template Application
```typescript
async function applyTemplateToProject(
  projectId: string,
  templateId: string,
  userId: string
): Promise<{
  equipmentCreated: number;
  foldersCreated: number;
  workflowStagesCreated: number;
  checklistItemsCreated: number;
}>
```

**Behavior**:
1. Validate project is empty
2. Create transaction
3. Clone `TemplateEquipment` → `Equipment` (generate new CUIDs)
4. Clone `TemplateFolder` → folders (maintain hierarchy)
5. Clone `TemplateWorkflowStage` → workflow config
6. Clone `TemplateChecklistItem` → checklist
7. Log to audit vault with full template snapshot
8. Set `Project.templateId`

#### Sandbox Creation
```typescript
async function createSandboxProject(
  sourceProjectId: string,
  userId: string
): Promise<string> // Returns sandbox projectId
```

**Behavior**:
1. Clone project with all equipment, documents (structure only, no files)
2. Set `isSandbox=true`
3. Set expiration date (30 days)
4. Mark as read-only
5. Return sandbox ID

#### Change Proposal
```typescript
async function applySandboxChanges(
  liveProjectId: string,
  sandboxProjectId: string,
  changeProposalText: string,
  userId: string,
  requiresApproval: boolean
): Promise<{ proposalId?: string; applied: boolean }>
```

**Behavior**:
1. Compute diff between sandbox and live project
2. If `requiresApproval=true`, create change proposal workflow
3. If `requiresApproval=false` (user has `PROJECT_CHANGE_APPROVE`), apply immediately
4. Log full diff to audit vault
5. Delete sandbox after application

### Key Features

#### Sandbox/Simulation Mode
- Project Managers create `isSandbox=true` clone
- Sandbox projects are **READ-ONLY** for modifications
- Allows "what-if" scenario testing
- Sandbox expires after 30 days or can be promoted
- UI clearly shows "SANDBOX" badge

#### Template Application Rules
1. Templates can only be applied to **NEW** projects
2. Template application creates audit vault entry with full snapshot
3. After application, project becomes **independent** (no live link)
4. Template updates do NOT affect existing projects

#### Change Proposal Workflow
1. PM creates sandbox clone
2. PM tests changes in sandbox
3. PM submits Change Proposal with justification
4. Document Controller or Project Director approves
5. System applies changes with full audit trail

### Error Handling

- Prevent template application to non-empty projects
- Prevent deleting templates in use by projects
- Prevent modifying read-only sandbox projects
- Validate referential integrity during cloning
- Log all template operations to audit trail
