# P2P1: Equipment Hierarchy Management - Implementation Prompt

## Context

You are implementing **Phase 2, Prompt 1 (P2P1)** for **DocuRoute**, an ISO 9001 compliant document management system for shipbuilding, offshore platforms, and heavy industrial projects. DocuRoute is a pnpm monorepo with:
- **apps/web**: Next.js 14 app with NextAuth v4.24.13, TypeScript, Tailwind CSS
- **apps/worker**: Node.js BullMQ worker for background jobs
- **packages/db**: Prisma ORM with PostgreSQL (Supabase)
- **packages/core**: Shared business logic (no React/Next.js imports)
- **packages/types**: Shared TypeScript types
- **packages/emails**: React Email templates

**Phase 1 Status**: User authentication (NextAuth), PBAC authorization with 47 permissions, document upload with R2 storage, QR verification, custom roles, project management, invitations, document search, and notifications are fully implemented.

**Your Mission**: Implement Equipment Hierarchy Management to enable field engineers and commissioning teams to navigate equipment by location and system hierarchy, linking equipment to documents (drawings, manuals, datasheets).

model Equipment {
  id                String              @id @default(cuid())
  companyId         String
  projectId         String
  tag               String              // Unique equipment identifier (e.g., "ME-01", "P-101A")
  name              String              // Human-readable name

  tagNumber         Int?                // Sequential number (e.g., 001)

  level             Int                 // COMPUTED COLUMN - derived from parent chain

  // Lifecycle tracking

  commissionedAt    DateTime?
  decommissionedAt  DateTime?

  maintenanceType   String?             // "PREVENTIVE" | "CORRECTIVE" | "PREDICTIVE" | "RUN_TO_FAILURE"

  updatedAt         DateTime            @updatedAt

  company           Company             @relation(fields: [companyId], references: [id])
  project           Project             @relation(fields: [projectId], references: [id])

  @@index([companyId, projectId])
  @@index([parentId])  // CRITICAL for tree queries

  @@index([criticalityLevel])
  @@index([maintenanceType])
  @@index([tagPrefix, tagType])

### Level Computation (PostgreSQL Function)

Create a migration with this SQL function:

```sql
CREATE OR REPLACE FUNCTION compute_equipment_level(equipment_id TEXT)
RETURNS INT AS $$
WITH RECURSIVE hierarchy AS (
  SELECT id, parent_id, 0 AS level
  FROM "Equipment"
  WHERE id = equipment_id
  UNION ALL
  SELECT e.id, e.parent_id, h.level + 1
  FROM "Equipment" e
  JOIN hierarchy h ON e.parent_id = h.id
)
SELECT MAX(level) FROM hierarchy;
$$ LANGUAGE SQL STABLE;
```

### Performance
- Use appropriate database indexes (already in schema)
- **CRITICAL**: Avoid N+1 queries when loading equipment hierarchy
  - Use Prisma `include` to load parent/children in single query
  - Example: `prisma.equipment.findMany({ include: { parent: true, children: true } })`
- Batch operations for bulk imports (use `createMany()` not individual `create()`)
- Paginate equipment lists for large projects (default 50, max 100 per page)
- Consider N+1 query optimization for tree loading
- **CRITICAL**: When fetching equipment with documents, use:
  ```typescript
  await prisma.equipment.findMany({
    where: { projectId },
    include: {
      parent: true,
      children: true,
      documentMappings: {
        include: { document: true }
      }
    },
    orderBy: [
      { level: 'asc' },
      { tagPrefix: 'asc' },
      { tagNumber: 'asc' }
    ]
  })
  ```
- For equipment change logs, fetch in batches to avoid loading thousands of records

### Security
- Validate all user inputs with Zod
- Check permissions before mutations
- Prevent SQL injection via Prisma
- Log sensitive operations to audit trail
- Validate companyId isolation in multi-tenant queries
