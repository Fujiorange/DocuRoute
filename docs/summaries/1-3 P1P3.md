# P1P3 — Custom Role Management System: Implementation Summary

## Overview

This prompt (P1P3) implements the custom role management system for DocuRoute, enabling companies to create and manage custom roles with granular permission assignments. This builds on top of the Phase 0 authorization model (P0P5) and the authentication system (P1P2).

## What Was Built

### 1. API Routes (`apps/web/src/app/api/roles/`)

#### GET /api/roles
- **Purpose:** List all roles for the company (system + custom)
- **Permission Required:** `MANAGE_CUSTOM_ROLES`
- **Feature Gate:** Not required (listing always allowed)
- **Returns:**
  - All system roles with `isSystemRole: true`, `permissions: []` (empty array)
  - All custom roles with actual permissions array
  - User count for each role
- **Implementation:** Uses `getPrismaForCompany()` for company isolation

#### POST /api/roles
- **Purpose:** Create a new custom role
- **Permission Required:** `MANAGE_CUSTOM_ROLES` (live check)
- **Feature Gate:** REQUIRED — `customRoles` must be enabled
- **Validation:**
  - Name: 2-50 characters, unique within company
  - Permissions: Valid Permission enum values, no platform-only permissions
  - Description: Optional, max 500 characters
- **Audit:**
  - `AuditLog`: `CUSTOM_ROLE_CREATED`
  - `AuditVaultEntry`: `CUSTOM_ROLE_PERMISSION_CHANGE` with action `CREATED`
- **Implementation:** Uses Zod schema validation, explicit transaction handling

#### PATCH /api/roles/[id]
- **Purpose:** Update custom role (name, description, and/or permissions)
- **Permission Required:** `MANAGE_CUSTOM_ROLES` (live check)
- **Feature Gate:** REQUIRED — `customRoles` must be enabled
- **Validation:**
  - Cannot edit system roles (`isSystemRole: false` required)
  - New name must be unique (if changing name)
  - Platform-only permissions forbidden
- **Audit:**
  - `AuditLog`: `CUSTOM_ROLE_UPDATED` with change details
  - `AuditVaultEntry`: `CUSTOM_ROLE_PERMISSION_CHANGE` with action `UPDATED` (only if permissions changed)
- **Cross-company protection:** Returns 404 (not 403) for other companies' roles

#### DELETE /api/roles/[id]
- **Purpose:** Delete custom role
- **Permission Required:** `MANAGE_CUSTOM_ROLES` (live check)
- **Feature Gate:** REQUIRED — `customRoles` must be enabled
- **Validation:**
  - Cannot delete system roles
  - Cannot delete if users are assigned to the role
  - Error includes `usersCount` and `suggestReassignTo` fields
- **Audit:**
  - `AuditLog`: `CUSTOM_ROLE_DELETED`
  - `AuditVaultEntry`: `CUSTOM_ROLE_PERMISSION_CHANGE` with action `DELETED` and `hadPermissions`

#### PATCH /api/roles/[id]/permissions
- **Purpose:** Shortcut endpoint to update only permissions
- **Permission Required:** `MANAGE_CUSTOM_ROLES` (live check)
- **Feature Gate:** REQUIRED — `customRoles` must be enabled
- **Validation:** Same as PATCH /api/roles/[id] for permissions
- **Audit:** Same as PATCH /api/roles/[id]

### 2. Validation Schemas (`apps/web/src/lib/validations/role.ts`)

Three Zod schemas for input validation:

- **`createRoleSchema`**: Validates role creation
  - `name`: string, 2-50 chars
  - `description`: optional string, max 500 chars
  - `permissions`: array of Permission enum, min 1, no platform-only permissions

- **`updateRoleSchema`**: Validates role updates
  - All fields optional
  - Same constraints as creation schema

- **`updatePermissionsSchema`**: Validates permission-only updates
  - `permissions`: required array of Permission enum

**Platform-Only Permission Protection:**
All schemas reject `PLATFORM_ADMIN_ACCESS` and `EMERGENCY_TRANSFER` using Zod's `refine()` method.

### 3. Client-Side Permission Utilities

#### usePermissions Hook (`apps/web/src/hooks/use-permissions.ts`)
- **Purpose:** Client-side permission checking based on session JWT
- **Returns:**
  - `permissions`: Current user's permissions array
  - `hasPermission(p)`: Check if user has ONE permission
  - `hasAllPermissions(ps)`: Check if user has ALL permissions (AND logic)
  - `hasAnyPermission(ps)`: Check if user has ANY permission (OR logic)
  - `isLoading`: Session loading state
- **Important:** For UI display only. Server-side checks are mandatory.

#### PermissionGate Component (`apps/web/src/components/users/permission-gate.tsx`)
- **Purpose:** Conditionally render UI based on permissions
- **Props:**
  - `requiredPermissions`: Permission[]
  - `children`: Content to show if authorized
  - `fallback`: Optional content to show if unauthorized
  - `requireAll`: Boolean (default false) — AND vs OR logic
- **Behavior:**
  - Returns `null` while loading (prevents content flash)
  - Shows children if user has required permissions
  - Shows fallback otherwise
- **Important:** For UI only. All API routes must check permissions independently.

### 4. UI Components (`apps/web/src/components/roles/`)

#### PermissionCheckboxGrid
- **Purpose:** Permission selection interface with categories
- **Features:**
  - 8 categories: Document Operations, MDR & Naming, Workflows, Transmittals, Team Management, Compliance & Legal, Security & Identity, Billing & Ownership
  - "Select All" / "Deselect All" per category
  - Amber "⚠ Sensitive" badges on: DELETE_DOCUMENT, HARD_PURGE_DOCUMENT, FORCE_UNLOCK_WORKFLOW
  - Responsive grid layout (1/2/3 columns)
  - Platform-only permissions (PLATFORM_ADMIN_ACCESS, EMERGENCY_TRANSFER, BYPASS_LEGAL_HOLD) are hidden entirely
- **Props:**
  - `selectedPermissions`: Current selection
  - `onChange`: Callback when selection changes
  - `disabled`: Disable all checkboxes

#### RoleBuilder
- **Purpose:** Form for creating/editing custom roles
- **Features:**
  - Name and description inputs
  - Department suggestion chips (from `DEPARTMENT_SUGGESTIONS` constant)
  - Permission selection via PermissionCheckboxGrid
  - Form validation with react-hook-form + Zod
  - Loading state during submission
- **Props:**
  - `mode`: 'create' | 'edit'
  - `initialData`: Optional pre-filled data for editing
  - `onSubmit`: Async callback for form submission
  - `onCancel`: Callback for cancellation
- **Integration:** Uses `createRoleSchema` for validation

#### RoleList
- **Purpose:** Display and manage all roles (system + custom)
- **Features:**
  - Two sections: "System Roles" (read-only) and "Custom Roles" (editable)
  - System role cards show "Managed by system" tooltip
  - Custom role cards show Edit and Delete buttons
  - "Create Custom Role" button (hidden if feature not enabled)
  - Upgrade prompt if `customRoles` feature disabled
  - Dialog for creating/editing roles (uses RoleBuilder)
- **State Management:**
  - Fetches roles from GET /api/roles on mount
  - Refetches after create/update/delete operations
  - Loading and error states
- **Feature Detection:** Checks if `customRoles` feature is enabled (currently hardcoded to `true`, should be from session/company data in production)

### 5. Permission Categories

The following permission categories are used in the UI (39 permissions total):

1. **Document Operations** (9): Upload, view, download, delete, archive, hard purge, edit metadata, bulk ops, undo bulk
2. **MDR & Naming** (3): Import MDR, validate naming, configure naming
3. **Workflows** (5): Start, approve, reject, force unlock, manage templates
4. **Transmittals** (3): Create, send, view
5. **Team Management** (4): Invite, manage, deactivate users, manage custom roles
6. **Compliance & Legal** (6): Place/lift/bypass legal hold, configure retention, view audit log, export vault, manage holds
7. **Security & Identity** (5): Configure SSO, manage SCIM, create/revoke API keys, manage service accounts
8. **Billing & Ownership** (3): Manage billing, transfer ownership, configure succession

**Hidden from UI entirely:**
- `PLATFORM_ADMIN_ACCESS`
- `EMERGENCY_TRANSFER`
- `BYPASS_LEGAL_HOLD` (implicitly hidden, only COMPANY_OWNER has it)

## Key Design Decisions

### 1. Feature Gate Placement
The `requireFeature()` check is placed **FIRST** in all mutation routes (POST, PATCH, DELETE) before permission checks. This ensures that plan boundaries are enforced before any authorization logic runs.

GET /api/roles does **NOT** require the feature flag because listing roles is a basic administrative function needed for user management.

### 2. Live Permission Checks
All mutations use `requireLivePermission()` instead of `requirePermission()` to prevent JWT tampering. This fetches the user's current permissions from the database on every sensitive operation.

GET /api/roles uses regular `requirePermission()` because it's a read operation and doesn't modify data.

### 3. Audit Logging Strategy
- **AuditLog**: Used for all role operations (CREATED, UPDATED, DELETED)
- **AuditVaultEntry**: Used only for permission changes (compliance-critical)
  - Action metadata: 'CREATED', 'UPDATED', 'DELETED'
  - Includes `previousPermissions` and `newPermissions` for updates
  - Includes `hadPermissions` for deletions

### 4. Cross-Company Resource Protection
When a user requests a role from another company, the API returns **404 Not Found** instead of 403 Forbidden. This prevents information disclosure about other companies' resources.

### 5. System Role Protection
System roles (`isSystemRole: true`) cannot be edited or deleted. The API checks this and returns 403 Forbidden with a clear error message. This protects ISO 9001 compliance roles.

### 6. Transaction Usage
The current implementation does **NOT** use Prisma transactions because:
1. Each route performs a single database operation
2. Audit logging is async and non-blocking (never throws)

If future requirements need atomic operations (e.g., create role + assign users), transactions must be added with the TRANSACTION RULE: pass `companyId` explicitly in all `tx.model.create()` calls.

### 7. Platform-Only Permission Enforcement
Platform-only permissions are enforced at **three levels**:
1. **Zod validation**: Schema rejects them in input
2. **UI**: Hidden from PermissionCheckboxGrid entirely
3. **Documentation**: Clearly documented in permission list

### 8. Client-Side Permission Display
The `PermissionGate` component and `usePermissions` hook are for **UI display only**. They do not provide security. All API routes must independently verify permissions using `requirePermission()` or `requireLivePermission()`.

## Known Limitations & Future Improvements

1. **Feature Flag Detection:**
   Currently, `hasCustomRolesFeature` in `RoleList` component is hardcoded to `true`. This should be read from `session.user.company.features.customRoles` in production.

2. **Error Handling in UI:**
   The UI uses `alert()` for errors. Consider replacing with a toast notification system (e.g., sonner) for better UX.

3. **Real-time Updates:**
   Role list does not auto-refresh when roles are created/updated in another browser tab. Consider adding WebSocket or polling for real-time updates.

4. **Permission Search:**
   With 39 permissions, the PermissionCheckboxGrid can be overwhelming. Consider adding a search/filter feature.

5. **Role Templates:**
   Consider adding pre-defined role templates (e.g., "QA Inspector", "Site Supervisor") that users can clone and customize.

6. **Permission Descriptions:**
   The UI shows permission names (e.g., "Upload Document") but not detailed descriptions of what each permission allows. Consider adding tooltips with explanations.

7. **Bulk Permission Editing:**
   Currently, updating permissions requires editing the entire role. Consider adding a bulk "add/remove permission from multiple roles" feature.

8. **Role Hierarchy:**
   The current system is flat. Consider adding role inheritance (e.g., "Senior Engineer" inherits from "Engineer").

## Security Considerations

### ✅ Implemented Security Measures
1. **Live Permission Checks:** All mutations use `requireLivePermission()` to prevent JWT tampering
2. **Feature Gating:** All mutations check `requireFeature()` before executing
3. **Platform Permission Protection:** Triple-layered enforcement (Zod + UI + docs)
4. **System Role Protection:** Cannot edit or delete system roles
5. **Cross-Company Isolation:** Uses `getPrismaForCompany()` for company-scoped queries
6. **Audit Logging:** All operations logged to AuditLog and AuditVaultEntry
7. **Validation:** Zod schemas validate all inputs
8. **Error Handling:** `withApiHandler()` catches all errors and sanitizes responses

### ⚠️ Additional Recommendations
1. **Rate Limiting:** Consider adding rate limits to role management endpoints (e.g., max 100 role operations per hour per company)
2. **Role Name Sanitization:** Consider blocking role names that impersonate system roles (e.g., "Company Owner" with different casing)
3. **Permission Auditing:** Consider periodic audits of role permission assignments to detect anomalies
4. **MFA for Role Changes:** Consider requiring MFA re-authentication for sensitive role operations
