# P1P4 — User Management System: Implementation Summary

## Overview

This prompt (P1P4) implements the user management system for DocuRoute, enabling authorized users to invite new team members, manage user roles, and deactivate accounts. This builds on the authorization model (P0P5), authentication system (P1P2), and custom role management (P1P3).

## What Was Built

### 1. API Routes (`apps/web/src/app/api/users/`)

#### GET /api/users
- **Purpose:** List all users in the company with their role information
- **Permission Required:** `MANAGE_USERS` OR `INVITE_USERS` (OR logic)
- **Feature Gate:** Not required
- **Returns:**
  - User info: id, email, name, isActive, mfaEnabled, scimDeprovisioned
  - Full role details: roleId, role.name, role.isSystemRole, role.systemRoleKey, role.permissions
  - Activity timestamps: createdAt, updatedAt
- **Implementation:** Uses `getPrismaForCompany()` for automatic company isolation
- **Security:** Never returns users from other companies (extension handles this)

#### POST /api/users/invite
- **Purpose:** Create an invitation for a new user to join the company
- **Permission Required:** `INVITE_USERS` (live check)
- **Feature Gate:** Not required
- **Request Body:**
  ```json
  {
    "email": "user@company.com",
    "roleId": "role_id_string",
    "name": "Optional Name"
  }
  ```
- **Validation:**
  - Email: valid email format, not already exists, no pending invitation
  - RoleId: must belong to this company (FK validation)
  - Seat limit check: counts active users, excludes BILLING_CONTACT system role
  - Compares against `PLAN_LIMITS[planTier].users`
- **Seat Limit Response:**
  - Returns 402 Payment Required if at limit
  - Includes `{ code: 'SEAT_LIMIT_REACHED', limit, current }`
- **Invitation Details:**
  - Token: 32-byte random hex string
  - Expiry: 7 days from creation
  - Magic link format: `${NEXTAUTH_URL}/auth/accept-invite?token={token}`
- **Audit:**
  - `AuditLog`: `USER_INVITED`
  - Metadata: email, roleId, roleName, invitationId, expiresAt
  - PermissionsUsed: `[Permission.INVITE_USERS]`
- **Implementation Notes:**
  - Uses `prismaAdmin` for invitation creation (no companyId extension on Invitation table)
  - TODO: Send email via Resend (currently returns magic link in response for testing)

#### POST /api/users/[id]/role
- **Purpose:** Change a user's role assignment
- **Permission Required:** `MANAGE_USERS` (live check - role changes are sensitive)
- **Feature Gate:** Not required
- **Request Body:**
  ```json
  {
    "roleId": "new_role_id_string"
  }
  ```
- **Validation:**
  - RoleId must belong to this company
  - Cannot assign PLATFORM_ADMIN system role via this endpoint
  - COMPANY_ADMIN cannot assign COMPANY_OWNER role (ownership transfer territory)
  - Returns success immediately if role hasn't changed
- **Transaction Handling:**
  - Uses Prisma transaction for atomicity
  - **CRITICAL:** Passes companyId explicitly (extension doesn't apply in tx)
  - Updates user.roleId
  - Creates AuditLog entry with change details
- **Audit:**
  - `AuditLog`: `USER_ROLE_CHANGED`
  - Metadata: targetUserId, targetUserEmail, fromRoleId, fromRoleName, toRoleId, toRoleName
  - PermissionsUsed: `[Permission.MANAGE_USERS]`
- **Cross-company protection:** Returns 404 (not 403) for other companies' users

#### POST /api/users/[id]/deactivate
- **Purpose:** Deactivate a user account
- **Permission Required:** `DEACTIVATE_USERS` (live check)
- **Feature Gate:** Not required
- **Validation:**
  - Cannot deactivate yourself (checked by userId comparison)
  - Cannot deactivate the only user with COMPANY_OWNER system role
  - Checks if there are other active COMPANY_OWNER users
  - Returns success immediately if user already inactive
- **Transaction Handling:**
  - Uses Prisma transaction for atomicity
  - **CRITICAL:** Passes companyId explicitly
  - Sets user.isActive = false
  - Creates AuditLog entry
- **Audit:**
  - `AuditLog`: `USER_DEACTIVATED`
  - Metadata: targetUserId, targetUserEmail, targetUserName, roleId, roleName
  - PermissionsUsed: `[Permission.DEACTIVATE_USERS]`

### 2. Validation Schemas (`apps/web/src/lib/validations/user.ts`)

Two Zod schemas for input validation:

- **`inviteUserSchema`**: Validates user invitation
  - `email`: valid email, lowercase, trimmed
  - `roleId`: required string, min 1 char
  - `name`: optional string, 1-100 chars

- **`changeUserRoleSchema`**: Validates role change
  - `roleId`: required string, min 1 char

## Key Implementation Patterns

### 1. Permission Checks
- **API Routes:** Always use `requireLivePermission()` for mutations
- **UI Components:** Use `PermissionGate` for conditional rendering
- **Never:** Check role name strings - always use Permission enum

### 2. Database Operations
- **Queries:** Use `getPrismaForCompany(companyId)` for automatic isolation
- **Transactions:** Pass `companyId` explicitly in all data objects
- **Cross-company:** Use `prismaAdmin` only when documented (auth, SCIM, KMS)

### 3. Audit Logging
- **Standard Events:** Use `logAuditEvent()` for all mutations
- **Compliance Events:** Use `writeVaultEntry()` for sensitive operations (none in user management)
- **Always Include:** userId, companyId, action, permissionsUsed, metadata

### 4. Error Handling
- **User-facing:** Non-leaking errors via `DocuRouteError`
- **Cross-company:** Return 404 (not 403) for resource access
- **Validation:** Use Zod schemas with descriptive error messages
- **API:** Wrapped with `withApiHandler()` for consistent error responses

### 5. Seat Limit Enforcement
- **Count Calculation:** Active users excluding BILLING_CONTACT role
- **Plan Limits:** Retrieved from `PLAN_LIMITS[planTier]`
- **Response:** 402 Payment Required with actionable error message
- **UI Warning:** Proactive alerts at 80% and 100% capacity

## Security Considerations

### 1. Permission Enforcement
- ✅ Live permission checks on all mutations
- ✅ Session-based permission checks on read operations
- ✅ UI permission gates are display-only (server validates)
- ✅ Never trust client-side permission state

### 2. Data Isolation
- ✅ `getPrismaForCompany()` ensures company-scoped queries
- ✅ Explicit companyId in all transactions
- ✅ Cross-company requests return 404 (not 403)
- ✅ Role validation ensures FK belongs to company

### 3. Privilege Escalation Prevention
- ✅ Cannot assign PLATFORM_ADMIN via user management
- ✅ COMPANY_ADMIN cannot assign COMPANY_OWNER
- ✅ Cannot deactivate yourself
- ✅ Cannot deactivate the only COMPANY_OWNER

### 4. Audit Trail
- ✅ All mutations logged to AuditLog
- ✅ permissionsUsed array on every audit entry
- ✅ Detailed metadata for compliance tracking
- ✅ ipAddress and userAgent captured when available

### 5. Input Validation
- ✅ Zod schemas validate all inputs
- ✅ Email format validation
- ✅ Role FK validation
- ✅ Duplicate invitation prevention

## Integration Points

### With P0P5 (Authorization Model)
- Uses Permission enum for all checks
- Resolves permissions from SYSTEM_ROLE_PERMISSIONS
- Uses PLAN_LIMITS for seat enforcement
- References SystemRoleKey type

### With P1P2 (Authentication)
- Uses `getServerSession(authOptions)` for session
- Calls `requireLivePermission()` for mutations
- Integrates with NextAuth JWT strategy
- Uses existing session structure

### With P1P3 (Custom Roles)
- Fetches roles from GET /api/roles
- Displays custom roles with "Custom" badge
- Uses role permissions for authorization
- Shares role-related types and validations
