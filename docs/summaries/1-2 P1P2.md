This prompt (Phase 1, Prompt 2) completes the authentication and Permission-Based Access Control (PBAC) middleware for DocuRoute, building on the Phase 0 infrastructure established in Prompt #5.

- **Provider**: Email magic link via Resend
- **Adapter**: PrismaAdapter for email verification
- **Session**: 30-day max age

**Callbacks**:

**`signIn`**
- Blocks inactive users (`isActive: false`)

- Logs `SESSION_STARTED` to AuditLog with metadata

**`session`**
- Exposes token data to client
- Maps all JWT fields to `session.user` object

**Events**:
- `signOut`: Logs `SESSION_ENDED` to AuditLog

**Pages**:
- Sign in: `/login`
- Verify request: `/verify-request`
- Error: `/auth/error`

## Architecture Decisions

### JWT Strategy vs Database Sessions

**Decision**: JWT-only sessions (not database sessions)

**Rationale**:
- Simpler implementation for pilot phase
- Better performance (no database query on every request)
- For permission revocation: `requireLivePermission()` re-fetches current state from DB

**Trade-offs**:
- JWT permissions may become stale if role is updated since login
- Mitigated by using `requireLivePermission()` for all sensitive operations
- Database session management deferred to post-pilot

### Permission Storage in JWT

**Decision**: Store full `Permission[]` array in JWT

**Rationale**:
- Eliminates DB query for permission checks on read operations
- Fast authorization for view/list endpoints
- Acceptable staleness for read operations

**Critical Rule**:
- Mutations MUST use `requireLivePermission()` to re-check current permissions
- This includes: role changes, user deactivation, legal holds, SSO config, API keys, ownership transfer, audit vault exports, custom roles

### PrismaAdmin Usage

All `prismaAdmin` usage in auth context is intentional and documented:

1. **`resolvePermissions()`**: Needs to look up Role by ID without companyId filter (called during session creation)
2. **NextAuth callbacks**: Need to look up any user by email across all companies
3. **`requireLivePermission()`**: Must fetch live, unfiltered user record for sensitive operations
4. **`requireFeature()`**: Needs to look up Company without companyId filter

## Security Features

### Permission Revocation

**Problem**: JWT permissions are cached in token, so role changes don't take effect immediately.

**Solution**:
- `requireLivePermission()` re-fetches user from DB before sensitive operations
- Checks: user is active, companyId matches session, current permissions allow operation
- Throws 401 if user inactive or companyId mismatch (JWT tampering detection)
- Throws 403 if permission not in allowed set
- Logs `PERMISSION_DENIED` to AuditLog with operation details

### Inactive User Blocking

**Implementation**: `signIn` callback checks `user.isActive` before allowing authentication

**Protection**:
- Inactive users cannot sign in (magic link won't be sent or won't work)
- Existing sessions: `requireLivePermission()` checks `isActive` on sensitive operations

### JWT Tampering Detection

**Protection**: `requireLivePermission()` verifies `companyId` matches session
- If mismatch: throws 401 (JWT tampering suspected)
- Prevents cross-company access via modified tokens

### Audit Logging

All authentication events are logged:
- `SESSION_STARTED`: On successful sign-in (with email, roleName)
- `SESSION_ENDED`: On sign-out
- `PERMISSION_DENIED`: On failed permission checks (with operation, allowed, actual permissions)

### Compliance Violation Handling

`withApiHandler` automatically:
- Catches `DocuRouteError` with `category: 'COMPLIANCE_VIOLATION'`
- Writes to `AuditVaultEntry` before returning response
- Uses `AuditVaultEventType.BREAK_GLASS_ACCESS`
- Never exposes stack traces or DB details

## Usage Examples

### In API Routes

```typescript
import { getServerSession } from 'next-auth'
import { authOptions } from '@/app/api/auth/[...nextauth]/route'
import { requirePermission, requireLivePermission } from '@/lib/auth'
import { Permission } from '@docuroute/types'
import { withApiHandler } from '@/lib/auth'

export const GET = withApiHandler(async (req: Request) => {
  // Get session
  const session = await getServerSession(authOptions)

  // Convert to ResolvedUser
  const user = session?.user ? {
    userId: session.user.userId,
    companyId: session.user.companyId,
    permissions: session.user.permissions,
    roleName: session.user.roleName,
  } : null

  // For read operations: use JWT permissions
  requirePermission(user, [Permission.VIEW_DOCUMENT])

  // For mutations: use live permission check
  await requireLivePermission(
    user,
    [Permission.DELETE_DOCUMENT],
    'delete document',
    req.headers.get('x-forwarded-for'),
    req.headers.get('user-agent')
  )

  // Your logic here...
})
```

### In Client Components

```typescript
'use client'

import { useSession, signIn, signOut } from 'next-auth/react'
import { Permission } from '@docuroute/types'

export function MyComponent() {
  const { data: session, status } = useSession()

  if (status === 'loading') return <div>Loading...</div>
  if (!session) return <button onClick={() => signIn()}>Sign in</button>

  const canUpload = session.user.permissions.includes(Permission.UPLOAD_DOCUMENT)

  return (
    <div>
      <p>Signed in as {session.user.email}</p>
      <p>Role: {session.user.roleName}</p>
      {canUpload && <button>Upload Document</button>}
      <button onClick={() => signOut()}>Sign out</button>
    </div>
  )
}
```

## Known Limitations

1. **Permission Staleness**: JWT permissions may be stale until next login
   - **Mitigation**: `requireLivePermission()` for all mutations

2. **Session Revocation**: Cannot force-revoke active sessions
   - **Mitigation**: Deactivate user → next operation fails via `requireLivePermission()`
   - **Future**: Database session management for instant revocation

3. **MFA**: Not yet implemented
   - `mfaVerified: false` in all tokens
   - **Future**: Phase 3 will add MFA support

4. **Email Provider**: Currently configured for Resend
   - **Future**: Support multiple email providers
