### 2. **Rate Limiting**

#### `/packages/core/src/rate-limit.ts` (115 lines)
- **Sliding window algorithm** using Upstash Redis
- `checkRateLimit(config)`: Validates and increments counter, throws `rateLimitExceeded()` if limit exceeded
- `getRateLimitStatus(config)`: Read-only check (doesn't increment)
- Redis key format: `ratelimit:{key}` with sorted set (timestamps as scores)
- Automatic cleanup via TTL (2× window duration)

### 3. **API Endpoints**

#### `/apps/web/src/app/api/invitations/accept/route.ts` (195 lines)
**Endpoint**: `POST /api/invitations/accept`
- **Authentication**: None (invitation token IS the authentication)
- **Input**: `{ token: string, name: string }`
- **Flow**:
  1. Validate token (exists, not expired, not accepted)
  2. Check for existing user with same email
  3. **Transaction** (Prisma `$transaction`):
     - Create User with `roleId` from Invitation (FK)
     - Mark Invitation as accepted (`acceptedAt = now()`)
     - Update/create CompanyOnboarding: add `'FIRST_TEAM_MEMBER_INVITED'` to `completedSteps`
  4. Log audit event: `USER_INVITED` with `{ invitationAccepted: true }`
- **Returns**: HTTP 201 with user details
- **Error logging**: Invalid/expired tokens logged as `PERMISSION_DENIED` with `tokenPrefix` (first 8 chars)

#### `/apps/web/src/app/api/invitations/resend/route.ts` (198 lines)
**Endpoint**: `POST /api/invitations/resend`
- **Permission**: `INVITE_USERS` (live check via `requireLivePermission`)
- **Input**: `{ invitationId: string }`
- **Rate limit**: 3 resends per email per 24 hours (`checkRateLimit()`)
- **Flow**:
  1. Validate invitation (exists, not accepted, not expired)
  2. Check rate limit (throws HTTP 429 if exceeded)
  3. Generate new token, extend expiry (+7 days)
  4. Update Invitation record
  5. Send email via `sendInvitationEmail()`
  6. Log audit: `USER_INVITED` with `{ resent: true }`
- **Returns**: HTTP 200 with updated invitation details

#### `/apps/web/src/app/api/invitations/validate/route.ts` (95 lines)
**Endpoint**: `POST /api/invitations/validate`
- **Authentication**: None (used by accept-invite page pre-submission)
- **Input**: `{ token: string }`
- **Returns**:
  - email, roleName, isSystemRole, systemRoleKey, permissions, companyName, expiresAt
  - Permissions resolved via `resolvePermissionsFromRole()`
- **Used by**: Accept-invite form to display role details before user submits

## Key Technical Decisions

### 1. **Rate Limiting Strategy**
- **Why Redis?** Accurate sliding window, persistent across server restarts, distributed-safe
- **Why Upstash?** Serverless-friendly (REST API), no persistent connection required
- **Sliding window vs Fixed window**: Sliding prevents burst attacks at window boundaries
- **3 resends per 24h**: Balances user convenience with spam prevention

### 2. **Email Failure Handling**
- **Decision**: Email failures don't fail invitation creation/resend
- **Rationale**:
  1. Invitation token is valid and reusable via resend
  2. Temporary email provider issues shouldn't block user management
  3. Logged for monitoring but not user-facing

### 3. **Token Security**
- **Storage**: Plaintext in DB (indexed for fast lookup)
- **Logging**: Only first 8 chars (`tokenPrefix`) logged in audit events
- **Why not hashed?** Tokens are one-time-use (acceptedAt prevents reuse), expiry enforced, no password-level security needed
- **Crypto**: `crypto.randomBytes(32)` provides 256 bits of entropy

### 4. **Auto Sign-In After Accept**
- **Current**: Uses NextAuth v4 `signIn('credentials')` — requires email/password provider
- **Limitation**: User must manually log in if email provider not configured
- **Future**: Implement magic link auto-login (session creation on accept)

### 5. **CompanyOnboarding Step Tracking**
- **Upsert logic**: Check if step exists before adding (idempotent)
- **Creation**: If no CompanyOnboarding record, create with `['FIRST_TEAM_MEMBER_INVITED']`
- **Steps tracked**: FIRST_PROJECT_CREATED, FIRST_DOCUMENT_UPLOADED, FIRST_TEAM_MEMBER_INVITED, NAMING_MASK_CONFIGURED, FIRST_WORKFLOW_STARTED

## Database Operations

### Prisma Transaction Usage

#### `POST /api/invitations/accept` Transaction
```typescript
prismaAdmin.$transaction(async (tx) => {
  // CRITICAL: companyId passed explicitly (tx doesn't inherit extension)
  const user = await tx.user.create({
    data: { email, name, companyId, roleId, isActive: true }
  })

  await tx.invitation.update({
    where: { id },
    data: { acceptedAt: new Date() }
  })

  await tx.companyOnboarding.upsert({
    where: { companyId },
    update: { completedSteps: [...existing, 'FIRST_TEAM_MEMBER_INVITED'] },
    create: { companyId, completedSteps: ['FIRST_TEAM_MEMBER_INVITED'] }
  })
})
```

**Why `prismaAdmin`?**
- Invitation table has no companyId extension
- Need to write across User and Invitation tables atomically

### Index Usage
- `Invitation.token` (unique index) — fast lookup on accept/validate
- `Invitation (email, companyId)` (compound index) — duplicate check on invite
- `User (companyId, isActive)` — seat count queries

## Error Handling

### User-Facing Errors
- `"Invalid or expired invitation"` (token not found / expired)
- `"This invitation has already been accepted"` (acceptedAt != null)
- `"A user with this email already exists"` (duplicate email)
- `"Too many resend attempts"` (rate limit exceeded)

### Audit Log Entries (Non-User-Facing)
- `PERMISSION_DENIED` with `{ reason: 'INVALID_INVITATION_TOKEN', tokenPrefix }`
- `PERMISSION_DENIED` with `{ reason: 'EXPIRED_INVITATION_TOKEN', tokenPrefix, email }`

### Email Delivery Failures
- Logged to console: `console.error('Failed to send invitation email:', error)`
- HTTP response: 201 (invitation created) — email failure doesn't fail request

## Known Limitations

1. **Auto Sign-In**: Currently requires manual login after accept (NextAuth v4 limitation)
2. **Email Queue**: Resend API called synchronously (no retry queue for failures)
3. **Rate Limit Fallback**: No in-memory fallback if Redis unavailable
4. **Token Expiry Job**: No scheduled job to clean up expired invitations (DB accumulation over time)
