1. EXECUTIVE SUMMARY
================================================================================

DocuRoute is a sophisticated document management SaaS platform designed for
regulated heavy industries (marine, oil & gas, construction). Built as a
TypeScript monorepo with Next.js 15, Prisma, PostgreSQL, BullMQ, and Go
microservices.

CORE VALUE PROPOSITION:
- Compliance-first: Immutable audit vault, retention policies, legal holds
- Field-ready: QR code verification for offline construction sites
- Multi-tenant: Scalable from pilot to enterprise (3-pillar strategy)
- Permission-based: 86 atomic permissions, 6 system roles, unlimited custom
- Industry-specific: Engineering disciplines, issue purposes, transmittals

TECHNICAL HIGHLIGHTS:
- 15 database models with pg_trgm fuzzy search & GIN indexes
- 68 API routes covering documents, workflows, transmittals, compliance
- 2 background workers (Node.js BullMQ + Go PDF processor)
- 8 cron jobs for retention, vault integrity, workflow timeouts
- Hybrid PBAC (Permission-Based Access Control + System Roles)
- Redis permission caching (version-aware, 1-hour TTL)
- Immutable audit vault (database trigger-enforced)
- Progressive Web App (offline support via IndexedDB)
- SCIM 2.0 user provisioning (Azure AD, Okta, Google Workspace)

7. AUTHENTICATION & AUTHORIZATION
================================================================================

AUTHENTICATION:
- Provider: NextAuth v4 (stable, NOT beta)
- Method: Magic link (passwordless) via Resend
- Session Storage: JWT in HTTP-only cookies
- JWT Claims:
  - userId, companyId, roleId, permissionVersion
  - No permissions in JWT (stored in Redis cache)

AUTHORIZATION MODEL: Hybrid PBAC + System Roles

WHY HYBRID:
- ISO 9001 & DNV/ABS audits require named roles ("Document Controller approved revision B")
- Custom roles provide organizational flexibility
- Both are mandatory for compliance

PERMISSION RESOLUTION:
```
1. User → roleId (FK to Role table)
2. Role → isSystemRole ?
   - YES: permissions = SYSTEM_ROLE_PERMISSIONS[systemRoleKey]
   - NO: permissions = role.permissions[] (custom role)
3. requirePermission(session, [Permission.UPLOAD_DOCUMENT])
```

SYSTEM ROLES (Immutable):
- PLATFORM_ADMIN - Platform operations, emergency transfers
- COMPANY_OWNER - All permissions except platform-only
- COMPANY_ADMIN - Full company management
- DOCUMENT_CONTROLLER - Document lifecycle, workflows, transmittals
- AUDITOR - Read-only audit access
- BILLING_CONTACT - Billing management only

CUSTOM ROLES (DB-driven):
- Companies create roles with any Permission subset
- Plan-gated: Tier 2+ only (checked via requireFeature())
- Stored in Role.permissions[] as enum array

PERMISSION CACHING (Critical Performance Optimization):
```
Problem: JWT cookie bloat (1440 bytes with 86 permissions)
Solution: Store permissions in Redis, version in JWT

JWT: { userId, companyId, roleId, permissionVersion: 1 }
Redis: "permissions:company123:role456:v1" → ["UPLOAD_DOCUMENT", ...]

On permission change:
1. Increment version in Redis
2. Cache new permissions with new version
3. User's next request detects version mismatch
4. Middleware auto-refreshes from DB
```

PERMISSION CHECK FUNCTIONS:
- requirePermission(session, [Permission.UPLOAD]) - OR logic (any permission)
- requirePermissions(session, [Permission.A, Permission.B]) - AND logic (all)
- requireLivePermission(session, [...]) - Fetches fresh from DB (sensitive ops)

MULTI-TENANCY ENFORCEMENT:
- Middleware verifies session.companyId === user.companyId
- Prisma client factory: getPrismaForCompany(companyId)
- RLS-ready: Pillar 2 (app-level filtering), Pillar 3 (per-tenant DB routing)

8. MULTI-TENANCY ARCHITECTURE
================================================================================

THREE-PILLAR STRATEGY:

PILLAR 1: Application-Level Filtering (Current)
- All queries include companyId filter
- getPrismaForCompany(companyId) returns filtered client
- Fast, simple, works for pilot/SMB

PILLAR 2: Row-Level Security (RLS-Ready)
- PostgreSQL RLS policies enforce current_setting('app.company_id') = companyId
- Migration 20260323_rls_multi_tenancy sets up infrastructure
- Activated per table via ALTER TABLE ... ENABLE ROW LEVEL SECURITY
- Double-check against application logic errors

DESIGN PRINCIPLES:
1. Permission enum drives ALL authorization - Never check role names
2. Atomic actions - Each Permission is a single operation
3. Composable - requirePermission([A, B]) = user needs A OR B
4. Auditable - Every action logs permissionsUsed[]

PERFORMANCE OPTIMIZATIONS:
1. Pre-computed COMPANY_OWNER permissions - Filtered at module load
2. Redis caching - 1-hour TTL, version-aware
3. Single DB query - requireLivePermission() includes role fetch
4. GIN index - Fast permission queries: permissions @> ARRAY['UPLOAD_DOCUMENT']

PERMISSION LIFECYCLE:
```
1. User assigned to role → roleId FK
2. Login → JWT with permissionVersion
3. First request → Middleware caches permissions in Redis
4. Subsequent requests → Read from cache
5. Role updated → Increment version
6. Next request → Version mismatch → Auto-refresh from DB
```

10.1 DOCUMENT MANAGEMENT
-------------------------

UPLOAD PIPELINE:
1. User requests presigned URL: POST /api/upload/presign
   - Validates file type, size (<500MB)
   - Generates R2 presigned URL
   - Returns { uploadUrl, fileKey }
2. Client uploads directly to R2 (bypasses web server)
3. Client confirms upload: POST /api/upload/confirm
   - Creates Document record (status: PENDING)
   - Queues virus scan (VirusTotal API)
   - Queues watermark job (BullMQ)
4. Watermark worker processes:
   - Calls Go pdf-worker service
   - Generates QR code with documentId + revisionId
   - Applies watermark + QR to PDF footer
   - Uploads watermarked version to R2
   - Updates Document (status: ACTIVE, watermarkStatus: COMPLETE)

DOCUMENT STATUSES:
- PENDING → virus scan + watermark
- ACTIVE → ready for use
- SUPERSEDED → newer revision exists
- ARCHIVED → soft delete (recycle bin)
- DELETED → hard deleted after retention
- QUARANTINED → malware detected

WATERMARK STATUSES:
- PENDING → queued
- PROCESSING → worker processing
- COMPLETE → watermarked file available
- FAILED → processing error
- SKIPPED_TOO_LARGE → file >200MB (limit for pdf-lib)
- SKIPPED_ENCRYPTED → PDF password-protected

INDUSTRY FIELDS (Required):
- Discipline: Engineering discipline (PIPING, STRUCTURAL, ELECTRICAL, etc.)
- Issue Purpose: Document status (FOR_CONSTRUCTION, FOR_APPROVAL, AS_BUILT, etc.)

FEATURES:
- Full-text search with pg_trgm (fuzzy matching)
- Bulk operations (delete, archive, move to project)
- Undo window (30 minutes default, configurable)
- Recycle bin (90 days default, configurable)
- Legal holds (prevent deletion)

10.4 APPROVAL WORKFLOWS
------------------------

Architecture: State machine with multi-stage approvals

WORKFLOW TEMPLATES:
- Internal Review (2 stages)
- Client Approval (2 stages)
- Construction Release (3 stages)

STAGE DEFINITION:
```typescript
{
  stageNumber: 1,
  name: 'Technical Review',
  type: 'REVIEW' | 'APPROVAL',
  requiredPermission: Permission.APPROVE_WORKFLOW,
  requiredApprovals: 1,
  allowReject: true,
  timeoutHours: 48
}
```

FLOW:
1. Start workflow: POST /api/workflows/start
   - Creates WorkflowInstance record
   - Current stage: 1
   - Status: ACTIVE

2. User with required permission approves: POST /api/workflows/{id}/action
   - Records approval + timestamp
   - If stage approvals met → advance to next stage
   - If all stages complete → Status: COMPLETED
   - Sends notifications to next stage approvers

3. Timeout handling: Cron /api/cron/workflow-timeout
   - Query workflows where stageStartedAt + timeoutHours < now
   - Notify DOCUMENT_CONTROLLER
   - Option: auto-escalate or force unlock

FORCE UNLOCK: Permission.FORCE_UNLOCK_WORKFLOW
- Allows DOCUMENT_CONTROLLER to bypass stuck workflow
- Writes AuditVaultEntry: WORKFLOW_FORCE_UNLOCKED
