# P1P3 — Custom Role Management System: Test Guide

This document provides a beginner-friendly test guide for the custom role management system implemented in P1P3.

## Prerequisites

Before testing, ensure:
1. You have a running DocuRoute instance (local or staging)
2. You have access to the database (Supabase dashboard or psql)
3. You have at least one company created with the `customRoles` feature enabled
4. You have a test user with `MANAGE_CUSTOM_ROLES` permission

## Setting Up Test Environment

### Enable Custom Roles Feature for Test Company

Run this SQL in your Supabase SQL Editor:

```sql
-- Update your test company to enable customRoles feature
UPDATE "Company"
SET features = jsonb_set(
  COALESCE(features, '{}'::jsonb),
  '{customRoles}',
  'true'
)
WHERE id = 'YOUR_COMPANY_ID';

-- Verify the feature is enabled
SELECT id, name, features FROM "Company" WHERE id = 'YOUR_COMPANY_ID';
```

### Create Test User with MANAGE_CUSTOM_ROLES Permission

```sql
-- First, find or create a COMPANY_ADMIN role (system role with MANAGE_CUSTOM_ROLES)
SELECT id, name, "systemRoleKey" FROM "Role" 
WHERE "companyId" = 'YOUR_COMPANY_ID' 
AND "isSystemRole" = true 
AND "systemRoleKey" = 'COMPANY_ADMIN';

-- Assign your test user to this role
UPDATE "User"
SET "roleId" = 'ROLE_ID_FROM_ABOVE'
WHERE email = 'your-test-email@example.com';
```

## Test Cases

### Test 1: List All Roles (GET /api/roles)

**Purpose:** Verify that the API returns all system and custom roles for the company.

**Steps:**
1. Log in to the application as your test user
2. Navigate to `/dashboard/settings/roles` (or directly call the API)
3. Open browser DevTools → Network tab
4. The GET request to `/api/roles` should return 200 OK

**Expected Response:**
```json
{
  "roles": [
    {
      "id": "...",
      "name": "Company Owner",
      "description": null,
      "isSystemRole": true,
      "systemRoleKey": "COMPANY_OWNER",
      "permissions": [],  // Empty for system roles
      "userCount": 1,
      "createdAt": "...",
      "updatedAt": "..."
    },
    // ... other system roles ...
    // ... custom roles if any ...
  ]
}
```

**Pass Criteria:**
- ✅ Response status is 200
- ✅ Response contains all 6 system roles (COMPANY_OWNER, COMPANY_ADMIN, DOCUMENT_CONTROLLER, AUDITOR, BILLING_CONTACT, PLATFORM_ADMIN)
- ✅ System roles have `isSystemRole: true` and `permissions: []`
- ✅ `userCount` matches actual user assignments
- ❌ If 403: User lacks `MANAGE_CUSTOM_ROLES` permission
- ❌ If 401: User not authenticated

### Test 2: Create Custom Role (POST /api/roles)

**Purpose:** Verify that a custom role can be created with permissions.

**Steps:**
1. From the roles page, click "Create Custom Role"
2. Fill in the form:
   - **Name:** "Site Operations Manager"
   - **Description:** "Manages day-to-day site operations and document workflows"
   - **Permissions:** Select:
     - UPLOAD_DOCUMENT
     - VIEW_DOCUMENT
     - DOWNLOAD_DOCUMENT
     - EDIT_DOCUMENT_METADATA
     - START_WORKFLOW
     - APPROVE_WORKFLOW
3. Click "Create Role"

**Expected Behavior:**
- Form submits successfully
- New role appears in the Custom Roles section
- Browser console shows POST `/api/roles` → 201 Created

**Pass Criteria:**
- ✅ Role created successfully
- ✅ Appears in role list immediately
- ✅ `AuditLog` entry created with action `CUSTOM_ROLE_CREATED`
- ✅ `AuditVaultEntry` created with eventType `CUSTOM_ROLE_PERMISSION_CHANGE` and action `CREATED`
- ❌ If 403 "Feature not enabled": Company lacks `customRoles` feature
- ❌ If 403 "Permission denied": User lacks `MANAGE_CUSTOM_ROLES`
- ❌ If 422 "Role name exists": Name already used (try different name)

**Verify in Database:**
```sql
-- Check the role was created
SELECT * FROM "Role" 
WHERE "companyId" = 'YOUR_COMPANY_ID' 
AND name = 'Site Operations Manager';

-- Check audit log entry
SELECT * FROM "AuditLog" 
WHERE "companyId" = 'YOUR_COMPANY_ID' 
AND action = 'CUSTOM_ROLE_CREATED'
ORDER BY "createdAt" DESC LIMIT 1;

-- Check audit vault entry
SELECT * FROM "AuditVaultEntry" 
WHERE "companyId" = 'YOUR_COMPANY_ID' 
AND "eventType" = 'CUSTOM_ROLE_PERMISSION_CHANGE'
ORDER BY "createdAt" DESC LIMIT 1;
```

### Test 3: Validation — Platform-Only Permissions

**Purpose:** Verify that platform-only permissions cannot be assigned to custom roles.

**Steps:**
1. Click "Create Custom Role"
2. Manually craft a request using browser console or Postman:

```javascript
fetch('/api/roles', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    name: 'Malicious Admin',
    permissions: ['MANAGE_USERS', 'PLATFORM_ADMIN_ACCESS']  // ❌ Platform-only
  })
})
```

**Expected Response:**
```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "permissions: Platform-only permissions (PLATFORM_ADMIN_ACCESS, EMERGENCY_TRANSFER) cannot be assigned to custom roles"
  }
}
```

**Pass Criteria:**
- ✅ Request rejected with 422 status
- ✅ Error message clearly indicates platform-only permissions are forbidden
- ❌ If role is created: CRITICAL BUG — escalate immediately

### Test 4: Update Custom Role (PATCH /api/roles/[id])

**Purpose:** Verify that custom roles can be updated.

**Steps:**
1. From the role list, click "Edit" on the "Site Operations Manager" role created earlier
2. Update the description to: "Updated: Manages site operations and approvals"
3. Add permission: `REJECT_WORKFLOW`
4. Click "Update Role"

**Expected Behavior:**
- Role updates successfully
- Changes reflected immediately in the role list
- Browser console shows PATCH `/api/roles/{id}` → 200 OK

**Pass Criteria:**
- ✅ Role updated successfully
- ✅ Description changed
- ✅ New permission added to the role
- ✅ `AuditLog` entry with action `CUSTOM_ROLE_UPDATED`
- ✅ `AuditVaultEntry` with action `UPDATED` and both `previousPermissions` and `newPermissions`
- ❌ If 403: Feature gate or permission check failed
- ❌ If 404: Role not found or belongs to different company

**Verify Users See Updated Permissions:**
Note: Users with this role will see the updated permissions **at their next login** (JWT refresh). For immediate enforcement, sensitive operations use `requireLivePermission()` which fetches fresh data from the database.

### Test 10: Audit Trail Verification

**Purpose:** Verify that all role operations are properly audited.

**Steps:**
1. Perform the following operations:
   - Create a custom role
   - Update the role's permissions
   - Delete the role
2. Query the audit logs:

```sql
-- Check AuditLog entries
SELECT action, "resourceType", "resourceId", metadata, "createdAt"
FROM "AuditLog"
WHERE "companyId" = 'YOUR_COMPANY_ID'
AND action IN ('CUSTOM_ROLE_CREATED', 'CUSTOM_ROLE_UPDATED', 'CUSTOM_ROLE_DELETED')
ORDER BY "createdAt" DESC;

-- Check AuditVaultEntry entries
SELECT "eventType", metadata, hash, "createdAt"
FROM "AuditVaultEntry"
WHERE "companyId" = 'YOUR_COMPANY_ID'
AND "eventType" = 'CUSTOM_ROLE_PERMISSION_CHANGE'
ORDER BY "createdAt" DESC;
```

**Pass Criteria:**
- ✅ Each operation has corresponding AuditLog entry
- ✅ Permission changes have AuditVaultEntry (compliance-critical)
- ✅ Vault entries have valid SHA-256 hash in `hash` field
- ✅ Metadata includes:
  - `action`: 'CREATED', 'UPDATED', or 'DELETED'
  - `roleName`: Name of the role
  - `permissions`: Current permissions (for CREATED/UPDATED)
  - `previousPermissions` and `newPermissions` (for UPDATED)
  - `hadPermissions` (for DELETED)
- ❌ If any entry is missing: BUG — audit trail incomplete

## Common Issues and Troubleshooting

### Issue 1: 401 Unauthorized
**Cause:** Session expired or user not logged in  
**Fix:** Log in again

### Issue 2: 403 Forbidden — Feature not enabled
**Cause:** Company's `features.customRoles` is false/null  
**Fix:** Run SQL to enable feature (see Test 7)

### Issue 3: 403 Forbidden — Permission denied
**Cause:** User lacks `MANAGE_CUSTOM_ROLES` permission  
**Fix:** Assign user to a role with this permission (e.g., COMPANY_ADMIN)

### Issue 4: 422 Validation Error — Duplicate name
**Cause:** Role name already exists in company  
**Fix:** Use a unique name

### Issue 5: UI not showing updated permissions
**Cause:** JWT not refreshed yet  
**Fix:** Log out and log back in, or wait for token refresh

### Issue 6: TypeScript errors in components
**Cause:** Missing UI component imports  
**Fix:** Ensure all shadcn/ui components are installed:
```bash
pnpm dlx shadcn@latest add button card dialog input label badge separator alert
```

## Notes for Developers

1. **Live Permission Checks:** The `requireLivePermission()` function is used for all mutations to ensure permission checks are up-to-date, even if the user's JWT has stale permissions.

2. **Transactions:** Role creation, update, and deletion are not wrapped in transactions in the current implementation. Consider adding transactions if you need atomicity with related operations.

3. **Feature Flags:** The `customRoles` feature flag is stored in `Company.features` JSON field. Check this before showing UI elements related to custom roles.

4. **Immutable Audit Vault:** The `AuditVaultEntry` table has a PostgreSQL trigger that prevents UPDATE and DELETE operations. Never attempt to modify vault entries directly.

5. **Permission Resolution:** System role permissions are resolved from the `SYSTEM_ROLE_PERMISSIONS` constant in `@docuroute/types`. Custom role permissions are stored in the `Role.permissions` array field.
